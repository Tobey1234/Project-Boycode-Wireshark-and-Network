# PProject 1: Analyzing DNS, TCP, HTTP & TLS Traffic with Wireshark
By Akintayo Emmanuel A

Overview
This project explores how a typical web browsing session works under the hood — from typing a URL to loading a secure page — by capturing and analysing live network traffic using Wireshark on a Kali Linux VM. The goal was to observe, packet by packet, the four-layer chain that makes up nearly every web request:

DNS → TCP → TLS → HTTP/HTTPS

Objectives
Capture and interpret DNS queries and responses
Understand the TCP three-way handshake and connection lifecycle
Compare plaintext HTTP traffic against encrypted HTTPS/TLS traffic
Analyze the TLS handshake (Client Hello, Server Hello, Certificate exchange)
Demonstrate, with real evidence, why HTTPS protects data in transit
Tools Used
Wireshark 4.6.6 — packet capture and analysis
Kali Linux (VirtualBox VM)
Firefox — browser used to generate traffic
curl — used for a controlled, cache-free HTTP request
Test domains: example.com, iana.org, neverssl.com
Methodology
For each protocol, the same basic process was followed:

Start a Wireshark capture on the eth0 interface
Generate the relevant traffic (visit a site, or run a request)
Stop the capture
Apply a display filter to isolate the protocol of interest
Inspect individual packets in Wireshark's detail pane
Screenshot and document key findings
Part 1: DNS Traffic
Filter used: dns

DNS is the first step in loading any website — it translates a human-readable domain name (e.g. example.com) into a numeric IP address a computer can actually connect to.

Findings:

A DNS query packet showed the browser asking 172.20.26.19 (the configured resolver) for records on example.com — specifically an A record (IPv4 address) and an AAAA record (IPv6 address), plus a modern HTTPS record type used by browsers for connection hints.
The matching response packet (matched via a shared Transaction ID, e.g. 0xfb88) returned two valid IPv4 addresses: 104.20.23.154 and 172.66.147.243, along with a TTL (Time to Live) of 300 seconds — telling the browser how long it could reuse this answer before asking again.
DNS operates over UDP (port 17) rather than TCP, since it's a lightweight, single-shot question-and-answer exchange rather than a sustained conversation.
Part 2: TCP Traffic
Filter used: tcp, then tcp.flags.syn==1 to locate handshakes

Once an IP address is known, TCP establishes a reliable connection to it before any real data is exchanged.

The Three-Way Handshake:

1. Client → Server   [SYN]        "I'd like to connect"
2. Server → Client   [SYN, ACK]   "Acknowledged — I'd like to connect too"
3. Client → Server   [ACK]        "Confirmed — connection open"
This exact pattern was captured cleanly on a connection to 172.66.147.243:443 (packets 7, 8, 20), immediately followed by TLS negotiation and encrypted application data — demonstrating the full connection lifecycle in sequence.

A notable edge case was also observed: one of three parallel connection attempts (browsers often try multiple server IPs at once for speed/reliability) completed its SYN/SYN-ACK exchange but was then terminated with an RST (Reset) flag rather than a plain ACK. This is normal "happy eyeballs" behavior — once one connection succeeds, the browser cancels the redundant ones.

TCP Flags observed:

Flag	Meaning
SYN	Start a new connection
ACK	Acknowledge received data
PSH	Push data to the application immediately, don't buffer
RST	Abruptly reset/cancel a connection
FIN	Gracefully close a connection
Follow TCP Stream:

Reassembling a full HTTPS conversation (Follow → TCP Stream) showed 7,399 bytes of data across 5 client and 6 server packets — but the content itself was unreadable, scrambled ciphertext, since the connection was TLS-encrypted. Only the SNI (example.com) and negotiated protocol (http/1.1) were visible in plaintext, as these are exchanged before encryption fully engages.

Part 3: HTTP Traffic
Filter used: http

Site used: neverssl.com (a site deliberately kept on plain HTTP, since most modern sites force HTTPS)

This section captured a plaintext HTTP GET request and response, generated by Firefox's own connectivity-check request to detectportal.firefox.com/success.txt?ipv4.

Request :

GET /success.txt?ipv4 HTTP/1.1
Host: detectportal.firefox.com
User-Agent: Mozilla/5.0 (X11; Linux x86_64; rv:140.0) Gecko/20100101 Firefox/140.0
Accept: */*
Accept-Language: en-US,en;q=0.5
Accept-Encoding: gzip, deflate
Connection: keep-alive
Cache-Control: no-cache
Response (packet 291):

HTTP/1.1 200 OK
Connection: close
Content-Length: 8
Server: Varnish
Content-Type: text/plain
X-Cache: MISS
Cache-Control: public, must-revalidate, max-age=0, s-maxage=3600

success
Key observation:

Every header — browser type, OS, language preference, even the server software (Varnish) — was fully readable in plain text. Follow HTTP Stream confirmed this: the entire request and response, including the actual returned content (success), was visible with zero obfuscation.

This stands in direct contrast to the encrypted TLS stream from Part 2 — the single clearest illustration in this project of why HTTPS matters: over plain HTTP, anyone capturing traffic on the same network (e.g. public Wi-Fi) can read this information exactly as easily as we just did.

Part 4: TLS Traffic
Filter used: tls, then tls.handshake.type==1 (Client Hello) and ==2 (Server Hello)

Site used: example.com / iana.org

Client Hello :

The browser's opening message — sent before encryption is active — included:

SNI (Server Name Indication):example.com— the only part of this exchange visible to network observers
17 supported cipher suites offered for the server to choose from
A random number, used later as an ingredient in generating the session's encryption key
A Session ID, allowing faster reconnection later
Server Hello (packet 36):

The server's reply:

Cipher Suite chosen: TLS_AES_256_GCM_SHA384 — AES-256 encryption, GCM mode for integrity, SHA-384 hashing
Its own random number, combined with the client's to independently derive a shared secret key on both ends — without the key itself ever crossing the network
A key_share extension using elliptic curve secp256r1, enabling secure key exchange
Certificate:

Because this capture used TLS 1.3, the certificate exchange itself is encrypted and not visible directly in Wireshark (unlike older TLS 1.2). Instead, the certificate was inspected via Firefox's built-in certificate viewer:

Field	Value
Domain	www.iana.org
Validity	Aug 21, 2026 – Nov 19, 2026
Public Key Algorithm	Elliptic Curve (256-bit)
Signature Algorithm	ECDSA with SHA-256
Certificate Authority	No (end-entity certificate)
This certificate is the server's proof of identity — verified and digitally signed by a trusted Certificate Authority, checked by the browser against the domain name, validity window, and trust chain before the padlock icon is shown.

Encrypted Application Data:

A packet carrying real page content post-handshake showed only:

Encrypted Application Data: f4a47b71526462017be4ff243ef60e613073d34e9e9d80f90176db1ed6504a1007d6
Completely unreadable, confirming the "locked door" is fully sealed at this point in the connection.

Summary: Tying the Flow Together
Step	Protocol	Purpose	Data Visibility
1	DNS	Resolve domain name → IP address	Fully readable
2	TCP	Establish a reliable connection	Metadata readable (no payload yet)
3	TLS	Negotiate encryption, verify identity	Handshake mostly readable; certificate encrypted (TLS 1.3)
4	HTTP/HTTPS	Exchange the actual request/content	Plaintext (HTTP) or fully encrypted (HTTPS)
This project demonstrated, with direct packet-level evidence, both how the modern web establishes connections and why encryption (TLS/HTTPS) is essential — by directly comparing a plaintext HTTP conversation against its fully-encrypted TLS counterpart on the same network.
